# Phase 9 Final Report

## 1. Phase 9 Objective
Harden the frontend ↔ backend API contract so that successful responses, validation errors, authentication failures, authorization failures, missing resources, conflicts, and unexpected server errors behave consistently and predictably. Centralize frontend error handling to present user-friendly alerts instead of generic crashes.

## 2. API Audit Scope
Inspected the FastAPI global setup (`main.py`), and all backend API routing layers (`auth.py`, `lots.py`, `offers.py`, `transactions.py`, `deps.py`, `advisor.py`). On the frontend, audited `api.js` which manages API calls, and analyzed how validation arrays (`422`) and string errors (`401`, `403`, `404`, `409`) are passed down to React components.

## 3. Endpoint / Error-Contract Findings
- **422 Unprocessable Entity**: Automatically generated by FastAPI Pydantic validation (as an array of missing fields), but the frontend failed to elegantly serialize it into string notifications.
- **500 Internal Server Error**: FastAPI leaked full stack traces if an unexpected bug/SQLAlchemy unhandled exception fired under `DEBUG=True`.
- **Frontend `api.js`**: Many standard unauthenticated endpoints (like `getMarketPrices`) or standard POSTs checked `!response.ok` and forcefully threw hardcoded strings (e.g., `throw new Error('Failed to fetch...')`) instead of reading the backend's explicit `detail` JSON key. 

## 4. Changes Made
- **Backend Global Exception Handler**: Added `@app.exception_handler(Exception)` in `backend/app/main.py`. It securely logs raw traces to the terminal using `logging` but forces a sanitized `{"detail": "Internal Server Error"}` 500 response back to the client.
- **Frontend Centralization**: Created a central `handleApiResponse(response)` async utility in `frontend/src/services/api.js`. It standardizes parsing of `{"detail": "..."}` for all error states. It intelligently formats FastAPI `422` arrays into comma-separated readable strings (e.g., `body.price: Input should be a valid number`). All endpoints now utilize this wrapper.

## 5. Authentication Error Behavior (401)
- Verified `401` behavior across the board. The centralized frontend `handleApiResponse` specifically intercepts `401`, emits the global `auth_error` event (which forces React to log the user out to `/login`), and halts subsequent execution safely. 

## 6. Authorization Error Behavior (403)
- IDOR (Insecure Direct Object Reference) attempts and cross-role violations correctly yield a `403 Forbidden` response. The frontend now accurately plucks the specific FastAPI error string (e.g., "Only the seller of this transaction can update its status").

## 7. 404 Resource Behavior
- Validated via `test_api_contract.py`. Attempting to hit missing lots, offers, or transactions cleanly returns `404 Not Found`.

## 8. 409 Conflict Behavior
- Verified state-machine transitions (e.g., accepting an offer that was already accepted, or paying an already paid transaction). The backend reliably returns `409 Conflict`. 

## 9. 422 Validation Behavior
- Verified structural validation. A malformed body or missing keys triggers a `422`. The frontend now successfully collapses the array into a human-readable string.

## 10. Frontend Error Handling
The frontend is heavily resilient. React components no longer deal with parsing backend JSON arrays or deducing HTTP statuses; `api.js` guarantees that `try/catch` blocks strictly receive a clean native JavaScript `Error` with a human-readable message.

## 11. API Contract Test Methodology
Created a Python test suite `backend/test_api_contract.py`. It boots `requests` HTTP calls to the local FastAPI server dynamically, simulating:
- Missing/invalid JWT
- Wrong role execution (Farmer creating an offer)
- Missing resources (Lot ID 9999)
- Invalid JSON body formats
- State machine concurrency conflicts (double-accepting an offer)
- Payment state backtracking
- Valid GET / POST routines
